## The audit

Six hard rules from §13. Each was checked against the code as it stands, not against what it was supposed to be.

### 1. Column ownership on every `report_` table

**The rule.** RLS is row-level: a policy letting somebody update "their own row" lets them update *every column* of it. This codebase has been caught by it three times, and §13 asks for every `report_` table to be checked.

**Method.** Listed every non-admin UPDATE or ALL policy across all seventeen tables from the database itself, and checked each against whether the table has a column guard.

| Table | Non-admin write | Guard | Verdict |
| --- | --- | --- | --- |
| `report_workspaces` | editors | yes | Blocks kind, owner, access window, first month |
| `report_periods` | editors | yes | Blocks publishing |
| `report_notes` | the author | yes | Blocks type, month, author, signature |
| `report_values` | editors | integrity only | **Finding 1** |
| `report_entities` | editors | integrity only | Safe — its guard checks a funnel's linked offer, and it carries no provenance columns |
| `report_launches` | editors | yes | Blocks publishing |
| `report_launch_values` | editors | integrity only | **Finding 1** |
| `report_targets` | editors | none | Safe — see below |
| `report_benchmarks` | editors | none | Safe |
| `report_launch_stages` | editors | none | Safe |
| `report_launch_prices` | editors | none | Safe |
| `report_top_items` | editors | none | Safe |
| `report_column_maps` | editors | none | Safe |
| `report_csv_imports` | insert only | n/a | Append-only, fixed 30 Sep |
| `report_metrics` | admin only | n/a | Reference data |
| `report_access` | admin only | n/a | Granted through functions |
| `report_reminders` | admin only | n/a | System bookkeeping |

**Why the five "none" rows are safe.** Each has a `with check` that re-evaluates on the row *after* the change, so an editor cannot move a target, benchmark, stage, price or top-3 item into a workspace or launch they do not already have write access to. Within their own workspace, changing which month or metric a target belongs to is editing the target, which is what the screen is for.

**FINDING 1 — audit columns are editable. Not fixed: needs a migration.**

`report_values` and `report_launch_values` each carry `entered_by`, `entered_at` and (on values) `source`. These are the record of *who typed a figure, when, and whether it came from a CSV*. An editor can rewrite all three on any row they can already edit.

Nobody can see another client's figures, so this is not a leak. It is a falsifiable audit trail: the one question these columns exist to answer — "where did this number come from" — can be answered wrongly by the same people who might need to be asked. The CSV import log was fixed for exactly this reason on 30 September; these three columns are the same argument on a different table.

The fix is a guard trigger of the shape already used four times in this schema. It is a migration, so it is written down here and not done:

```sql
-- aOS Reporting — a figure's provenance is the system's, not an editor's.
--
-- entered_by, entered_at and source answer "where did this number come
-- from". An editor can currently rewrite all three, which makes the answer
-- worth as much as whoever last edited it wanted it to be. Same argument as
-- report_csv_imports, fixed 30 September.

create or replace function public.guard_report_value_provenance()
returns trigger
language plpgsql
security definer
set search_path = ''
as $$
begin
  -- Admins and the service role set these legitimately; the CSV importer
  -- runs as the person doing the import and sets source = 'csv' on insert,
  -- which this does not touch.
  if public.is_portal_admin() or (select auth.uid()) is null then
    return new;
  end if;

  if new.entered_by is distinct from old.entered_by
     or new.source is distinct from old.source
  then
    raise exception 'Who entered a figure, and where it came from, is not editable';
  end if;

  -- entered_at moves forward on a real edit and must not move backward.
  if new.entered_at < old.entered_at then
    raise exception 'A figure cannot have been entered earlier than it was';
  end if;

  return new;
end;
$$;

create trigger report_values_guard_provenance
  before update on public.report_values
  for each row
  execute function public.guard_report_value_provenance();

create trigger report_launch_values_guard_provenance
  before update on public.report_launch_values
  for each row
  execute function public.guard_report_value_provenance();
```

One thing to decide before running it: the save path currently rewrites `entered_by` to the current editor on every update, which is correct — the last person to touch a figure is who entered it. The guard above would refuse that. Either the guard allows `entered_by` to change to *the person making the change* (not to an arbitrary third party), or the save stops rewriting it. The first is more useful and is what I would build; it needs the guard to compare against `auth.uid()` rather than against the old value.

### 2. The 1,000-row read limit

**The rule.** PostgREST caps a read at 1,000 rows and says nothing. §13: page or aggregate in SQL.

**Method.** Listed every query in the reporting feature and worked out what bounds each one.

| Query | Bound | Verdict |
| --- | --- | --- |
| `getMetrics` | 174 rows, fixed | Safe |
| `getMonthData` values | one workspace × two months | Safe |
| `getMonthData` entities / notes / period | one workspace | Safe |
| `getTrend` | explicit metric keys × months, month-level only | Safe by design |
| `getTargets` | one workspace | Safe — see note |
| `getBenchmarks` | one workspace, one per metric | Safe |
| `getPublishedMonths` | one workspace, months only | Safe |
| `getVisibleWorkspaces` | clients this login can see | Safe for a client; see note |
| Admin client list — workspaces, access, **periods** | **unbounded, months × clients** | **Was broken. Fixed in `b4c9ce3`.** |
| Save paths (`in` on metric keys) | one month's submitted fields | Safe |

**Fixed tonight.** The admin client list crossed the ceiling at roughly forty clients with two years of history, and would have rendered a page of quietly wrong counts. It now pages. Six tests, including the case where an exactly-full page is mistaken for the end.

**Two notes, neither urgent.** `getTargets` is bounded by metrics × entities for one workspace — a client with twenty offers and a target on every offer metric could theoretically approach the ceiling, though nothing in the product encourages that. `getVisibleWorkspaces` is unbounded for an admin specifically, and would break at 1,000 clients. Both are far enough away that paging them now would be noise; both are written here so the next person does not have to rediscover them.

### 3. Exactly one route per clickable thing

**Method.** Extracted every `href` in the reporting feature, including the ones built from template literals, and matched them against the routes that exist.

Every link resolves to one of four real routes: `/reporting`, `/reporting/[category]`, `/reporting/enter/[category]`, `/admin/reporting`. No dead links. The reverse also holds — every page has at least one route in: the Overview from the root and the tab row, a category from the tab row, an entry page from the "Enter data" button and the "Still to fill in" list, and the admin screen from both the sidebar and You.

Tabs for categories that have not shipped are **not drawn at all** rather than drawn and disabled, which is why the row shows six and not eleven. A test asserts every admin link in the sidebar has a page behind it.

**No finding.**

### 5. Drafts unreadable to the client at the database

**Method.** Asserted as the client's own session over RLS, not through the app.

- A retainer client reads zero figures and zero strategist notes for an unpublished month.
- Publishing releases the figures and the note together; unpublishing hides them again.
- Publishing one month does not release another.
- Twelve pages were scanned on 2 October for September's ten distinctive figures while September was a draft: **none appeared on any page**. Three values did appear on the August pages and all three are August's own published figures, which the client is entitled to see.
- A client cannot write a figure, cannot publish, and cannot write a strategist note — each refused by both the code and the database independently.

Mutating the code-side gate open does **not** let a client read a draft, because RLS refuses it separately. That is what §13's "both, never RLS alone" looks like when it works.

**No finding.**

### 6. Money ex-VAT

**The rule.** §13: all money figures are ex-VAT (net).

**Method.** Searched the whole reporting feature for any tax or VAT arithmetic.

There is none, which is correct — the rule is about what goes *in*, and the product should not be adding or removing tax anywhere. The formula module says so at the top.

**FINDING 2 — nothing on screen tells anyone the figures should be net. Not fixed: client-facing copy.**

A client entering Revenue from a gross invoice total produces a report that is wrong in a way nothing can detect. The fix is a few words — "ex-VAT" beside the money fields on the entry screens, or once at the top of Financials and Offers. It changes what a client sees, so it is written down rather than done. Nina may also have a preferred wording.

## Two further findings, outside the six rules

**FINDING 3 — `entered_by` can point at a deleted user. Not fixed: needs a migration.**

`report_values.entered_by` is `on delete set null`, so removing an auth user blanks who entered every figure they ever typed. That is the right choice over deleting the figures, but it means provenance is lost silently rather than kept as "someone who has since left". Storing the name alongside the id, as `report_notes` already does for exactly this reason, would keep it. Low priority; recorded because it is the same lesson learnt once already on notes.

**FINDING 4 — a stray `report_access` row has no screen. Not fixed: needs a screen, not a migration.**

A team member can be assigned to a client from `/admin/reporting`, and `unassign_report_team_member` exists to remove them — but nothing calls it. So an assignment can be made and not undone without editing the database. Internal-only, and not urgent while Elize is the only team member, but it is the same shape as the missing "edit client details" form that blocked the walkthrough on 2 October: **a field or action that can only be undone in the database is itself the bug.**

I did not fix it tonight because adding a destructive control to an admin screen without you seeing it first seemed like the wrong call under "don't stop the run".
